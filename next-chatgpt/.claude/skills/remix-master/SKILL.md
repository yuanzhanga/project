# 需求沟通 + 模板选定



**目标**：通过对话明确用户想做什么，内部选定模板，再按所选模板把需求**加深到足以驱动后续的无状态生成**，最终产出一份**结构化需求文档**。

整体流程：游戏创作有2阶段，本skill是第一阶段：需求澄清+产出yaml。第二阶段是一个流水线根据yaml机械执行。**二阶段无交互、无反馈回路**：本文档里每个模糊处，都会被生成器猜测填充并直接固化，没人复核。因此**宁可在一阶段问清，不要留白**。

**产出**：
1. 一份**机器可读的结构化需求文档**（YAML，见末尾 schema）
2. 选定的模板 id（写在文档 `meta.template_id`）


**注意**：
- **对用户零提及模板**——这是铁律。任何用户可见的文字（对话、需求摘要、确认话术、回退说明）里都不得出现"模板""template""形态""框架""目录""方案"等暗示存在预设载体的词。AI内部按模板机制运作，但对外只表现为"我在帮你把创意落成一个具体作品"。玩法形态的差异用题材/玩法/节奏等自然语言表达，不归因到"换了一种形态"。
- 只和用户确认**需求**，不和用户确认模板——模板由你内部根据需求直接选定。
- 必定从下方模板列表里选一个，不考虑"新建模板"或"部分匹配让用户选"。
- 本阶段产需求文档，**不写最终成稿文本，不生成素材**——那是二阶段的事。

## 入口模式

本 skill 有两个入口，决定 Step 2 怎么走：

- **从零（无模板）**：用户只有创意。按 Step 1 → Step 2 顺序，先聊清需求再选模板。
- **Remix（带入模板 id）**：用户从某个现有故事一键 remix，模板 id 已随入参传入。**优先沿用传入的模板**：跳过 Step 2 的自由选择，直接读它的 CONTENT_SPEC，把需求沟通（Step 1 + Step 3）围绕该模板的能力展开（例如它支持几个角色、是不是 AI 实时驱动）。**仅当**用户的想法明显超出该模板能力时——比如要数值/结局但模板是纯 AI 驱动、或角色数量对不上——才回退到 Step 2 的速查表重选模板，并向用户说明"这个玩法和原故事差别比较大，我换个方式来做"，**不得**提及"模板/形态/框架"等词。

## Step 1：聊清需求

**原则**：纯对话，不谈技术。不提模板、目录、框架、形态——用户不需要知道这些。用户感知到的应该是"AI 在帮我把想法落成作品"，而不是"AI 在帮我挑一个壳子"。

用户可能说得很模糊（"我想做一个恐怖游戏"）或很具体（"密室逃脱，3个房间，每间找5个线索"）。无论哪种，都从开放问题开始：

- 什么题材/风格？（恐怖、恋爱、悬疑、科幻、奇幻…）
- 核心玩法是什么？（解谜、对话、选择、卡牌、经营…）
- 玩家怎么交互？（点选、输入文字、拖拽、滑动…）
- 怎么算赢/怎么算结束？
- 大概想有多少内容？（几章？几个角色？几种结局？）

针对模糊或缺失的方面追问，**一次只问 1-2 个**，顺着回答自然推进：

| 方面 | 可能要问的问题 |
|------|-------------|
| **世界观/背景** | 故事发生在什么时候？什么地点？ |
| **角色** | 有几个重要角色？性格/作用？玩家扮演谁？ |
| **节奏** | 快节奏紧张感，还是慢节奏沉浸感？ |
| **结局** | 有多少种可能的结局？由什么决定？ |
| **长度** | 玩家玩完一遍大概多久？ |
| **参考** | 有没有类似的游戏或作品可参考风格？ |

聊到能判断玩法形态即可进入 Step 2。

## Step 2：选定模板（内部判断，不与用户确认）

- **Remix 入口**：模板已由入参给定，**默认沿用**，不走下面的自由选择；只有当需求明显超出该模板能力时才回退到速查表重选（见「入口模式」）。
- **从零入口**：对照下方「模板速查表」，根据已了解的需求选出最匹配的一个模板。优先选 `ready` 状态的模板。

无论哪种入口，模板一旦定下，**读该模板的 `workspace/templates_v2/<模板id>/CONTENT_SPEC.md`**，弄清它实际需要哪些内容域和资产——这是 Step 3 加深的依据。

## Step 3：模板感知加深

Step 1 的对话给的是方向，根据 Step 2 读到的 CONTENT_SPEC，针对该模板实际要落的内容域 + 资产清单，把以下维度逐项问到位（仍是自然语言提问，**不向用户暴露模板/字段术语**）：

| 加深维度 | 为什么必须问清（二阶段消费方） | 反例：留白会怎样 |
|---------|------------------------------|----------------|
| **视觉风格** → 画风 / 色板 / 光照 | 图片 prompt 强依赖；模板若要角色主题色也在此定 | 生成器自行选画风，风格漂移、色调不统一 |
| **每个角色的人设实质** → 性格 / 说话习惯 / 口头禅 / 与其他角色的语气区分 | 落到 `persona_brief`，二阶段据此拼出 AI system prompt 的人设部分；多角色模板要求各角色**明显区分** | 角色声音雷同，玩家分不清谁在说话 |
| **玩家视角/身份** → 玩家在故事里是谁 | 决定第二人称叙述、开场代入 | 生成器假设一个玩家身份，可能跑偏 |
| **开场基调** → prologue / 开场旁白要点 | 落到开场文本 | 开场氛围与题材不符 |
| **结束/结局**（仅模板支持时） | 结局文本与触发条件 | 无结局模板跳过此项 |
| **资产清单 + 每张图画什么 + 图间依赖** → 按 CONTENT_SPEC 逐项，问清主体/场景/构图，并识别哪些图需要先有别的图当参考 | 二阶段据此 + 视觉风格拼图片 prompt，并按依赖排生成顺序；缺主体只能瞎编画面，缺依赖会出现角色不一致 | 漏图、画面与故事无关、场景里的角色和角色图对不上 |
| **发布定位** → 分类标签 / 商店文案 / 角色音色 | 落到发布物料：tags 决定商店归类、商店标题简介是橱窗文案、每个会说话的角色要选 TTS 音色；二阶段据此拼 `manifest.json` + 提交音色任务。**封面视频默认生成**（标准发布物料），创意要点跟封面图一起在视觉风格里定 | 标签错放分类、橱窗文案空缺、音色乱配 |

**只问该模板实际需要的维度**：无数值/无结局的模板（如 duo-chat）不要问结局；单角色模板不要问多角色区分。**音色**只在模板有 TTS（角色会被朗读）时才问；纯文字模板跳过。

**音色选择**：每个会说话的角色按人设从下方「音色速查」里选一个 `voice_type`；拿不准时女声默认 `zh_female_wenroushunv_uranus_bigtts`（温柔淑女）、男声默认 `zh_male_yangguangqingnian_uranus_bigtts`（阳光青年）。**标签**必须从商店注册标签集里选（二阶段会对 `pub_res/tags.json` 校验），本阶段先按题材给出候选，落地以注册集为准。

**人设只产实质，不产格式**：本阶段把每个角色的人设描述清楚（`persona_brief`），**但不写** AI system prompt 的 JSON 输出契约、charId 绑定、fallback 等格式外壳——那些是模板自己的事，二阶段从模板注入。图片同理：本阶段定「画什么 + 什么风格」，最终 prompt 串（风格前缀 + 主体 + 无白边/规格后缀）由二阶段机械拼接。
