# 前端 Code Review

## 概述

对前端代码进行系统化、多维度的审查。每条发现必须标注所属维度、严重程度（🔴 严重 / 🟡 警告 / 🔵 建议），并附带具体的修复代码。

**核心原则**：不止于找出问题 — 要解释在浏览器/用户场景下为什么是个问题，并给出怎么改。

## 适用场景

- 用户说"帮我 review""code review""CR""检查一下这段代码"
- 合并包含 UI 改动的 feature 分支之前
- 用户粘贴或指向 `.tsx` / `.jsx` / `.vue` / `.css` / `.scss` 文件
- diff 中包含前端文件

**不适用场景：**
- 纯后端 / API 改动，不影响 UI → 用通用 code-review
- 配置文件修改（eslint、tsconfig 等）→ 属于工程基建，非前端范畴
- 用户明确要求其他类型的审查（安全审计、纯性能分析等）

## 审查流程

### 第一阶段：摸清项目上下文（必须先执行）

在审查任何代码之前，先读取项目配置，确保判断有据可依：

1. `package.json` — 框架版本（React 18 还是 19？Next.js pages 还是 app router？），关键依赖
2. `tsconfig.json` — 是否开启 strict？路径别名？编译目标？
3. Tailwind 配置 / CSS 框架设置 — 有哪些可用的工具类？
4. 项目级 CLAUDE.md 或约定文件

**为什么重要**：在 React 18 中是错误的写法（如用 `useEffect` 做派生状态），在 React 19 中可能是对的。如果项目约定不使用全局状态管理，那"props 层层传递"的抱怨就毫无意义。缺少上下文，发现的问题就是噪音。

### 第二阶段：评估规模，决定审查策略

**优先使用 MCP 工具（自动获取 diff + 分批），不要再手工跑 git 命令。**

```
1. 调用 MCP 工具 read_project_context 获取项目上下文（框架版本、TypeScript 配置等）
2. 调用 MCP 工具 review_code({ target: "用户指定的范围" })
   - 不传 target → 获取所有未提交改动（unstaged + staged）
   - 传 target: "main...HEAD" → 获取与 main 分支的差异
   - 传 target: "HEAD~5..HEAD" → 获取最近 5 个 commit
   - 传 files: [...] → 只审查指定文件
```

MCP 返回的 JSON 已包含：分桶结果、每批文件 diff、审查侧重点、推荐并发数。

**降级方案（MCP 不可用时）**：手工执行脚本
```bash
git diff --name-only <base>...HEAD | node .claude/skills/frontend-code-review/scripts/split-diff.mjs
```

脚本输出 JSON，策略决策逻辑：

| 规模 | 文件数 | 策略 |
|------|--------|------|
| **小** | ≤ 5 个 | **全量一次性审查**：通读所有文件，出一份完整报告 |
| **中** | 6 ~ 15 个 | **先分桶再分批**：按文件类型分桶 → 每桶一批，逐批审查 → 最终合并 |
| **大** | 16 ~ 30 个 | **分桶 + 并发 + 精简 diff**：分桶后每批只送变更摘要，并发审查，合并去重 |
| **超大** | > 30 个或 > 3000 行 diff | **降级策略**（见下方"超大变更降级"） |

**判断后必须告知用户**选择了哪种策略以及原因，让用户有心理预期。

---

### 第三阶段：分批审查执行

#### 3.1 分桶规则

将待审文件按以下优先级分桶（一个文件只归入一个桶）：

| 优先级 | 桶名 | 归类依据 | prompt 侧重点 |
|--------|------|---------|--------------|
| 1 | **组件/页面** | `.tsx` / `.jsx` / `.vue` / `.svelte` 文件 | 重点关注：Hook 规则、状态管理、无障碍、CSS、组件体积 |
| 2 | **Hook/逻辑** | `use*.ts` / `hooks/` 目录下的文件 | 重点关注：清理函数、依赖数组、闭包陷阱、竞态条件 |
| 3 | **工具/类型** | `utils/` / `lib/` / `types/` 目录下的文件 | 重点关注：类型安全、边界处理、纯函数正确性 |
| 4 | **样式** | `.css` / `.scss` / `.less` 文件 | 重点关注：响应式、动画性能、CSS 架构 |
| 5 | **测试** | `*.test.*` / `*.spec.*` / `__tests__/` 目录 | 重点关注：测试覆盖、异步测试完整性、实现细节断言 |

**如果文件之间有强依赖关系**（如 `User.vue` + `user.service.ts` + `user.controller.ts`），应合入同一桶，保留上下文。判断依据：文件间是否有 import 关系且改动互相影响。

#### 3.2 审查执行方式（按规模选择）

**小规模（≤5 文件）：手工逐文件审查**
1. `Read` 所有文件
2. 按下方"审查维度"全部过一遍
3. 直接输出审查报告

**中/大规模（>5 文件）：使用 Workflow 并发审查**

调用 `Workflow` 工具执行审查工作流，将分批计划 + 项目上下文作为参数传入：

```
Workflow(
  scriptPath: ".claude/skills/frontend-code-review/scripts/review-workflow.mjs",
  args: { batches, projectContext, strategy, maxFilesPerBatch }
)
```

Workflow 内部自动完成：
1. `parallel()` 启动每批一个独立 Agent，真正并行审查（最多 3 并发）
2. 每个 Agent 按 `FINDINGS_SCHEMA` 输出结构化 JSON
3. 合并去重：同一文件、同一维度、同一行的重复发现合并为一条
4. 按严重度排序：critical → warning → suggestion
5. 输出按维度、按文件的统计汇总

返回结果格式：
```json
{
  "summary": {
    "totalFiles": 12, "totalBatches": 4, "totalFindings": 23,
    "bySeverity": { "critical": 3, "warning": 12, "suggestion": 8 },
    "byDimension": { "React Hooks": 5, "性能": 3, ... },
    "byFile": { "src/a.ts": [...], ... }
  },
  "findings": [ ... ],
  "projectContext": { ... }
}
```

**注意**：Workflow 脚本里不能跑 git 命令，所以分批计划必须在调用前准备好（通过 MCP 或 split-diff.mjs）。

#### 3.3 并发与容错

- Workflow 的 `parallel()` 保证真正的并行执行，不会人工漏掉某批
- 单个批次审查失败 → 该批返回 `null`，不影响其他批次，合并时自动跳过
- Agent 的 `schema` 参数约束输出格式，杜绝"格式不对、字段缺失"的问题

#### 3.4 Token 控制

审查过程中需时刻注意 token 消耗：

| 控制项 | 阈值 |
|--------|------|
| 单文件 diff 上限 | 3000 字符（超出截断并标注） |
| 单批 diff 总上限 | 800 行 |
| 单次审查 prompt 上限 | ~8000 tokens（含 system prompt + diff） |
| 单文件审查超时 | 60 秒 |

**Diff 精简技巧**：
- 跳过纯空白行、纯注释行的变更
- import 语句的增删重排默认跳过（除非引入了不存在或废弃的模块）
- 大量相同模式的变更（如批量重命名）合并为一个发现而非逐行报告

#### 3.5 超大变更降级策略

当变更超过 **30 个文件** 或 diff 超过 **3000 行** 时，不要尝试全面审查，按以下优先级降级：

**降级方案 A：按优先级只审核心文件**
1. 先列出所有变更文件，标注每个文件的类型和风险等级
2. 只对以下文件进行详细审查：
   - 新增的组件/页面（`new_file: true`）
   - 涉及状态管理/Hook 的文件
   - 包含 `dangerouslySetInnerHTML` / `localStorage` / `router.push` 等高危模式的文件
3. 其余文件只检查红线清单（见末尾）是否触发
4. 报告中明确标注"本次审查了 X/Y 个核心文件，其余 Z 个文件仅做红线检查"

**降级方案 B：仅做结构性审查**
1. 不逐行审查 diff
2. 只检查以下全局特征：
   - 新增文件是否缺少测试文件
   - 组件/函数签名变更是否影响调用方
   - 新增依赖是否引入了重型包
   - 是否存在红线清单中的高危模式
3. 报告中明确标注"变更过大，仅做结构性审查，建议拆分 MR 或人工逐文件审查"

**降级方案 C：直接建议跳过**
如果变更超过 50 个文件且包含大量非前端文件，直接输出：
> ⚠️ 本次变更涉及 X 个文件、Y 行 diff，超出 AI 审查能力范围，建议：
> 1. 拆分为多个小型 MR，每个不超过 15 个文件
> 2. 或指定具体要审查的文件/目录，我按范围审查
> 3. 推荐人工逐文件 Review

**核心原则：宁可审查不完美，也不要因 token 超限或超时而完全失败。**

---

### 第四阶段：合并结果并输出

所有分批审查完成后，按以下步骤合并：

1. **去重**：同一文件同一行被多个批次标记的相同问题，合并为一条
2. **归类**：所有发现按维度分组，重新编号
3. **补充跨文件发现**：审查过程中如果发现跨文件的共性问题（如"所有组件都缺少 Error Boundary"），作为全局发现追加到报告开头
4. **输出最终报告**：按标准格式（维度 + 严重度 + 修复建议 + 总结表）输出

---

### 第五阶段：等待用户决策（必须执行）

审查报告输出完毕后，**必须**主动询问用户是否需要修复。根据用户回答执行：

- **用户说"修" / "帮我改" / "全修"** → 按严重度从高到低，逐文件应用所有修复
- **用户说"只修严重的" / "修 🔴 的"** → 只修复 🔴 严重级别的问题
- **用户说"修第 X 条"** → 只修指定编号的条目
- **用户说"再看看" / "不用" / "先这样"** → 不做任何修改，流程结束
- **用户没明确说修哪些但表达了意向** → 追问："是整个都修，还是只修 🔴 严重的几个？"

**修复时注意：**
- 每次修改前先 `Read` 目标文件，确认当前内容与审查时一致（文件可能已被手动改动）
- 修改后展示改动摘要（改了哪个文件、哪些行、怎么改的）
- 如果修复引入新问题（比如修复依赖数组导致无限循环），主动指出并给出处理建议

## 审查维度（每个文件必须全部过一遍）

### 1. React / 框架正确性

| 检查项 | 关注点 |
|-------|--------|
| **Hook 规则** | Hooks 是否在条件语句/循环/早 return 之后调用？ |
| **useEffect 清理** | 订阅、定时器、事件监听 — 是否在 return 中清理？缺少清理 = 内存泄漏 |
| **依赖数组** | 缺依赖 = 闭包陷阱 bug。多余依赖 = 无限循环。需逐一核验 |
| **useCallback / useMemo** | 是否确实需要（传给已 memo 的子组件）？还是徒增开销？ |
| **Key 属性** | 列表的 `key` — 是否稳定且唯一？可重排列表不能用 `index` |
| **条件化调用 Hook** | `if (x) useHook()` 非法 — Hook 必须在顶层调用 |
| **派生状态** | 值就是 `props.x + props.y` 的 state，应该直接计算，而不是 `useState` + `useEffect` |

### 2. 性能

| 检查项 | 关注点 |
|-------|--------|
| **不必要重渲染** | State 是否提升得太高？每次滚动/按键都 `setState` 导致整棵树重渲染？ |
| **缺失 memo** | 开销大的子组件是否未用 `React.memo` / `useMemo` 包裹？ |
| **JSX 内联对象** | `style={{...}}`、`onClick={() => ...}` — 每次渲染都是新引用，破坏 memo |
| **虚拟化** | 长列表（>100 条）是否没用虚拟滚动？ |
| **包体积** | 重型导入（moment、lodash 全量）— 建议改为可 tree-shake 的替代（`date-fns`、`lodash-es`） |
| **图片优化** | 用 `<img>` 而非 `next/image`？折叠线以下的图片缺少 `loading="lazy"`？ |
| **渲染中的昂贵计算** | 每次渲染都执行 `.filter().map().sort()` — 应放到 `useMemo` 中 |

### 3. 状态管理

| 检查项 | 关注点 |
|-------|--------|
| **直接修改 state** | `state.x = y` 而非 `setState({...state, x: y})`。数组用 `.push()` 直接修改 |
| **闭包陷阱** | 异步回调通过闭包读到旧 state — 应用 ref 或函数式更新 |
| **State 过度提升** | State 放在父组件，但只有一个子组件用到 |
| **缺少 loading/error 状态** | 数据请求没有 `loading`、`error`、空态处理 — UI 会闪白屏或卡死 |
| **竞态条件** | 多个异步请求 — 后返回的覆盖先返回的？缺少 `AbortController`？ |
| **Ref 滥用** | 5 个以上 ref 用于绕过闭包问题 = 架构设计有问题，不是解决方案 |

### 4. 无障碍（a11y）— WCAG 2.1 AA 标准

| 检查项 | 关注点 |
|-------|--------|
| **语义化 HTML** | 该用 `<button>`、`<nav>`、`<main>`、`<header>` 的地方用了 `<div>` |
| **颜色对比度** | 文字与背景 — 是否可读？尤其灰色文字在深色背景上 |
| **仅靠颜色传达信息** | 状态仅用颜色点（红/绿）表示 — 需要文字/图标替代方案 |
| **键盘导航** | 非交互元素上的 `onClick` 缺少 `onKeyDown`。Tab 顺序是否合理？ |
| **焦点管理** | 弹窗是否困住焦点？关闭后焦点是否恢复？焦点指示器是否可见？ |
| **ARIA 标签** | 交互元素缺少无障碍名称。仅图标的按钮需要 `aria-label` |
| **屏幕阅读器** | 装饰性 SVG/图片是否有 `aria-hidden="true"`？动态内容是否有 live region？ |
| **表单** | 输入框是否有 label（不能只有 placeholder）。错误信息是否通过 `aria-describedby` 关联？ |

### 5. CSS / 样式架构

| 检查项 | 关注点 |
|-------|--------|
| **响应式设计** | 写死 px 宽度导致移动端布局错乱。关键布局缺少断点适配 |
| **Tailwind 滥用** | `@apply` 过度使用、深层嵌套、用自定义 CSS 对抗工具类范式 |
| **CSS-in-JS 性能** | 每次渲染动态生成新 className |
| **动画性能** | 动画改变 `width`/`height`/`top`/`left` 而非 `transform`/`opacity`（GPU 加速） |
| **布局偏移 (CLS)** | 图片缺少 `width`/`height`。动态内容无骨架屏，直接推动布局 |

### 6. SSR / Next.js 专项

| 检查项 | 关注点 |
|-------|--------|
| **"use client" 边界** | 服务端组件干了客户端的事？客户端边界太靠上（整页）还是太细碎（闪烁）？ |
| **注水不匹配** | `Date.now()`、`Math.random()`、`localStorage` 出现在 render 中 → 注水报错 |
| **服务端 vs 客户端数据获取** | `useEffect` 中发请求，但本可以是异步服务端组件或 `getServerSideProps` |
| **动态导入** | 重型组件是否未用 `next/dynamic` 配合 `ssr: false` 或 loading 态？ |
| **Metadata** | 缺少 SEO 必需的 `metadata` 导出 — title、description、og:image |

### 7. 前端安全

| 检查项 | 关注点 |
|-------|--------|
| **XSS** | `dangerouslySetInnerHTML` 未消毒（需 DOMPurify）。用户输入直接作为 HTML 渲染 |
| **原型污染** | 用户输入的 `JSON.parse` 结果直接展开到对象中，或 `Object.assign` |
| **客户端敏感数据** | API Key、密钥、Token 出现在客户端代码或暴露给浏览器的 `.env` 中 |
| **开放重定向** | `router.push(userInput)` 未做校验 |

### 8. 代码质量与可维护性

| 检查项 | 关注点 |
|-------|--------|
| **组件体积** | 超过 200 行 — 应拆分为子组件或自定义 Hook |
| **魔法数字/字符串** | 硬编码值没有命名常量 |
| **错误边界** | 复杂功能区块缺少 Error Boundary 包裹 |
| **类型安全** | `as` 强制转换绕过类型检查。能用明确类型却用 `any` |
| **注释质量** | 注释在解释"做了什么"（代码已自明）而非"为什么这么做"（设计决策） |
| **死代码** | 注释掉的代码块、未使用的 import、不可达分支 |

### 9. 测试

| 检查项 | 关注点 |
|-------|--------|
| **新增 Hook 无测试** | 自定义 Hook 是纯逻辑单元，必须有单元测试。用 `@testing-library/react-hooks` 的 `renderHook` 或 `@testing-library/react` 的测试组件包裹验证其行为 |
| **新增组件无测试** | 新组件至少要有渲染测试（是否正常挂载）+ 关键交互测试（核心用户操作的输入/输出是否正确） |
| **复杂逻辑无覆盖** | 工具函数、状态机、数据转换函数 — 纯逻辑必须有单元测试覆盖边界情况 |
| **测试实现细节而非行为** | 测试在断 `state` 内部值、`setState` 调用次数、组件内部方法名 — 应改为断言用户看到的渲染结果和交互后的 DOM 变化 |
| **异步测试不完整** | 缺少 loading/error/success 三种状态的测试覆盖。异步操作没等 `waitFor` / `findBy*` 就断言 |
| **测试中的 act 警告** | 状态更新在 `act(...)` 之外发生 — 用 `waitFor` / `findBy*` 等异步查询代替手动 `act` |
| **快照测试滥用** | 大段快照测试代替行为断言 — 快照只适合稳定的静态结构（如纯展示组件），不能替代交互测试 |

## 输出格式

每条发现使用以下格式：

```
[维度] [严重度] 第 [N] 行：[一句话描述问题]
→ 修复：[具体的代码改动或操作]
```

**严重程度定义：**
- 🔴 **严重** — Bug、崩溃、数据丢失、安全漏洞、无障碍阻断。合入前**必须**修复。
- 🟡 **警告** — 性能问题、反模式、维护隐患。**应该**修复。
- 🔵 **建议** — 代码风格、小优化、替代方案。**可以**考虑。

按维度分组输出。末尾附总结表：

```
| 维度 | 🔴 | 🟡 | 🔵 |
|-----------|---|---|---|
| React 正确性 | 1 | 2 | 0 |
| 性能 | 0 | 1 | 1 |
| 测试 | 0 | 0 | 0 |
| ... | | | |
| **合计** | **X** | **Y** | **Z** |
```

## 审查禁忌（禁止行为）

### ❌ 不读项目配置就审查
不看 `package.json` 就说"用 React 19 的 use() hook"，结果项目是 React 18。**必须先读配置。**

### ❌ 只说"建议用 XXX"但不给代码
"建议用 useCallback"却不指明加在哪里、怎么写。**写不出具体修复代码，就不要提这条。**

### ❌ 重复标记 eslint 能覆盖的问题
如果项目 eslint 已经能检查到，并且通过了 lint，就不要重复提 — 说明"该项目 eslint 已覆盖此项"，然后跳过。

### ❌ 不标注严重程度
每条发现必须有严重度。"这里还行但可以更好" = 🔵 建议。

### ❌ 只挑毛病
如果某个模式写得很好（清理逻辑到位、组合设计优雅），简要提一句。Review 也应该认可好的实践。

## 常见前端问题速查

| 症状 | 可能原因 | 修复方向 |
|------|---------|---------|
| UI 加载时闪白屏 | 缺少 loading/空态处理，或 SSR 注水不匹配 | 加骨架屏或 `isMounted` 模式 |
| 输入时焦点丢失 | `key={Date.now()}` 或组件被重新挂载 | 使用稳定 key，调整 state 提升方式 |
| useEffect 无限循环 | 依赖数组中有对象/数组（每次渲染新引用） | 用 `useMemo` 包依赖，或改用原始类型依赖 |
| 滚动位置跳动 | DOM 更新先于滚动位置恢复 | 更新前存滚动位置，在 `useLayoutEffect` 中恢复 |
| 点击事件触发两次 | Strict Mode 双重调用 + 缺少清理 | 加 AbortController / 清理函数 |
| SPA 页面切换后内存增长 | 事件监听 / 订阅未清理 | `useEffect` return 清理函数 |

## 红线清单 — 以下问题一经发现，必须立即指出

- `dangerouslySetInnerHTML` 未做消毒处理 → 必须用 DOMPurify 或同类工具
- `useEffect` 缺少依赖数组，或用 `[]` 但内部使用了 props/state → 闭包陷阱 bug
- 在 React 中直接操作 DOM（`document.querySelector`、`element.appendChild`）→ 与框架对抗
- `setTimeout` / `setInterval` 无清理 → 组件卸载时必然内存泄漏
- 用户可控字符串的 `JSON.parse` 无 try-catch → 崩溃风险 + 原型污染
- 直接修改 state（`.push()`、原地 `.sort()`、`obj.x = y`）→ 隐蔽的渲染 bug
- API Key / 密钥仅存在于客户端代码 → 必须在服务端
- `new Date()` / `Math.random()` 出现在 render 函数体中（非事件处理/useEffect）→ SSR 注水不匹配
- 新增自定义 Hook 无单元测试 → 纯逻辑必须用 `renderHook` 验证行为；新增组件无渲染测试 → 至少要有挂载测试 + 关键交互测试
